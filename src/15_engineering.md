## A 工程能力如何分级
| 层级 | 先学会什么 | 交付 |
|---|---|---|
| Python 算法实验 | 文件处理、数组、配置、日志、异常 | 可复现实验脚本 |
| Linux 与 Git | 目录权限、进程、环境、分支和差异 | 可追踪的运行环境与代码 |
| 服务与部署 | 请求队列、批处理、超时、模型加载 | 可测的推理服务 |
| C++ 与端侧 | 内存、线程、缓冲、构建、剖析 | 固定硬件上的实时实现 |

C++ 不是所有语音模型实习的统一前置条件，但前端、嵌入式和性能岗位往往更重视它。学习顺序以你的目标岗位为准。

## B 音频块的状态不能随意丢
流式滤波、RNN 状态、卷积历史、注意力缓存都可能跨块依赖。每块重新初始化会产生边界断裂，或丢失上下文。

环形缓冲区管理连续输入；采集回调不宜执行可能长时间阻塞的工作。生产者与消费者速率不匹配，会产生丢帧、积压或播放中断。

测试连续音频、短片段、空输入、设备切换、采样率变化和异常恢复。不同设备时钟轻微差异也可能积累成对齐偏差。

## C RTF、吞吐与端到端时延
实时率 RTF 是处理耗时与音频时长的比值：

$$
\mathrm{RTF}=\frac{T_{\mathrm{proc}}}{T_{\mathrm{audio}}}
$$

$T_{\mathrm{proc}}$ 是处理耗时，$T_{\mathrm{audio}}>0$ 是对应音频时长，两者使用相同时间单位。处理 10 秒音频花 2 秒，则 $\mathrm{RTF}=\frac{2\,\mathrm{s}}{10\,\mathrm{s}}=0.2$。它没有告诉你第一帧何时可用。

| 指标 | 含义 |
|---|---|
| 首包时延 | 首个可消费输出出现多晚 |
| 算法时延 | 缓冲、分帧、未来信息等待等引入的延迟 |
| 端到端时延 | 从输入事件到用户收到结果的整体时间 |
| 吞吐 | 单位时间处理多少音频或请求 |
| P50/P95/P99 | 不同分位的响应表现 |

固定硬件、线程数、并发、精度、音频长度与预热条件。GPU 异步执行需要正确同步计时，否则容易把提交任务时间误当成计算时间。

## D 量化与模型压缩
PTQ 是训练后量化；QAT 在训练中模拟量化影响，帮助模型适应低精度。INT8、INT4 等描述位宽，但加速取决于硬件、算子和后端支持。

蒸馏让学生学习教师行为；剪枝减少部分结构或连接。非结构化稀疏不一定在普通硬件上加速。

模型体积缩小、参数更少，不代表实际运行更快。量化前后要同时比较 CER/WER、声音质量、内存和时延。

## E 部署与数值一致性
ONNX 等交换格式帮助衔接推理后端，但导出成功不表示动态长度、缓存和全部算子都正确。量化校准数据也应代表真实输入。

逐层或逐阶段比较原模型与部署结果。先固定输入，再确认采样率、归一化、特征、长度掩码、模型输出与后处理一致。

模型代码、权重、依赖版本和数据清单都要留档。只有一个无法复现的最优数字，对面试帮助有限。

## F 作业与自测
给一个已运行的模型建立性能表：预热前后、单请求与多个并发、浮点与量化条件。没有对应硬件就明确写未测，不补造数字。

| 问题 | 答案 |
|---|---|
| $\mathrm{RTF}<1$ 一定满足低延迟通话吗？ | 不一定，还可能等待完整片段或未来上下文 |
| INT4 一定比 INT8 快吗？ | 不一定，后端算子与硬件支持会影响结果 |
| 训练脚本能跑就不用学数据结构吗？ | 基础算法、复杂度与调试仍是常见通用能力 |

## 三种时间
| 指标 | 问题 |
|---|---|
| 实时率 | 整体计算能否跟上输入 |
| 首包时延 | 第一个结果何时出现 |
| 端到端时延 | 用户最终等多久 |
> 十秒音频两秒算完，实时率是零点二。
> 但如果先收齐十秒才能算，首包仍然很慢。
> 因此要测完整链路，不能只报模型运行时间。
## 分块要保留历史
```flow LR
前一个音频块 -> 状态缓存: 保存必要历史
新音频块 -> 当前推理: 读取输入
状态缓存 -> 当前推理: 延续时间上下文
```
> 不少模型和滤波器依赖过去的输入。
> 每块独立启动，可能造成断裂或质量下降。
> 正确管理状态，是流式实现的重要部分。
## 压缩后还要再测
| 方法 | 不能自动保证 |
|---|---|
| 更低位宽 | 一定更快 |
| 更少参数 | 一定更省端到端时延 |
| 成功导出 | 结果一定与原模型一致 |
> 硬件和后端决定能否利用压缩优势。
> 同时检查识别准确率或合成质量有没有退化。
> 你的项目应交付质量、速度和内存三方面的对照。
